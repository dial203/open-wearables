## In one paragraph

If the same brand reaches Open Wearables twice — once from the maker's API, once
relayed by Apple Health or another aggregator — reads show it once, and daily
summaries count it once. The relayed
copy is left out only for the span the direct connection actually covers, and
only for the data types it actually delivers. Nothing is deleted, every read can
ask for the hidden copies back, and one environment variable turns the whole
thing off.

    `RELAY_DEDUP_ENABLED=false` in the backend environment, then restart.
  </Card>
  <Card title="Turn it off for one read" icon="magnifying-glass">
    Add `include_redundant_relays=true` to the request.
  </Card>
  <Card title="Turn it off for one source" icon="toggle-on">
    `relay_visibility: "always"` on that data source, or **Keep it** on the
    user's Devices tab.
  </Card>
</CardGroup>

## Why this exists

Anyone running several brands ends up with both kinds of connection at once:

- **Direct** — the maker's own API. Garmin, Oura, Whoop, Polar, Withings, Fitbit.
- **Aggregator** — Apple Health, Google Health, Health Connect, Samsung Health,
  Strava. Needed because some devices have no other route: an Apple Watch, an
  app with no public API, a sensor that only writes into HealthKit.

An aggregator re-exposes everything on the phone, including the brands you
already read directly. The Oura ring you connected to Oura's API arrives a
second time as "Oura" inside Apple Health, the Garmin arrives again as
"Connect", and every listing, chart and export shows each device twice.

**The rule:** for the span the direct route actually covers, the aggregator's
copy of that same brand is left out of reads.

## What it does not hide

The rule is deliberately narrow, because hiding a device's only copy of a day
is far worse than showing it twice. It never hides:

    Coverage is measured from the samples that are really there. Connecting
    Garmin today does not blank out last year's Apple-relayed Garmin.
  </Card>
  <Card title="Data after a direct feed stops" icon="plug-circle-xmark">

    copy becomes visible again by itself.
  </Card>
  <Card title="A metric the maker's API never sends" icon="wave-pulse">
    Coverage is per series type. A stream only the aggregator carries is kept
    even while the rest of that brand is hidden.
  </Card>

    Two Garmins, one connected: a relayed source attributed to a device no

A brand with no direct integration at all — Zepp, Eight Sleep, a third-party
HealthKit writer — is never affected, and neither is an aggregator's own data
(an Apple Watch inside Apple Health is first-party, not a relay).

## The instance-wide switch

```bash
# backend/config/.env
RELAY_DEDUP_ENABLED=true   # default: hide the redundant copy
RELAY_DEDUP_ENABLED=false  # every source in every read, as before the rule existed
```

It is one flag covering the whole rule — time series, events, the per-source
overrides, all of it. Because nothing is ever deleted, flipping it is reversible
at any time: no migration, no re-sync, no data repair. The current setting is
reported by `GET /api/v1/config` as `relay_dedup_enabled`, and shown in the admin
panel under **Settings → Priorities**.

## Nothing is deleted

Ingest is unchanged: relayed rows keep being written exactly as before. The rule
filters reads only, and every read takes `include_redundant_relays=true` to get
the relayed copies back — for checking the direct route's completeness, or for
comparing the two paths against each other, which stays a supported analysis.

```bash
# Default: the redundant copy is left out
GET /api/v1/users/{user_id}/timeseries?types=heart_rate&start_time=...&end_time=...

# Everything, both routes
GET /api/v1/users/{user_id}/timeseries?types=heart_rate&include_redundant_relays=true&start_time=...&end_time=...
```

Applies to the time series endpoint, the event endpoints (workout, sleep,
menstrual cycle) and the daily summaries below. A read that names a single
`data_source_id` is never filtered: asking for a source by id is asking for
that source.

## Nothing disappears silently

When the rule leaves something out, the response says so in
`metadata.relay_dedup`:

```json
{
  "metadata": {
    "relay_dedup": {
      "applied": true,
      "hidden": [
        {
          "data_source_id": "8f14e45f-ceea-467a-9d2f-1b2c3d4e5f60",
          "provider": "apple",
          "brand": "Oura",
          "direct_provider": "oura",
          "covered_from": "2026-03-01T00:00:12Z",
          "covered_until": "2026-06-01T11:58:40Z",
          "reason": "covered_by_direct"
        }
      ]
    }
  }
}
```

`GET /api/v1/users/{user_id}/data-sources` carries the same classification per
source: `ingestion_route` (`direct` or `aggregator`), `redundant_relay`, the
`direct_provider` that made it redundant, and the `relay_visibility` override.

## Overriding it for one source

```bash
PATCH /api/v1/users/{user_id}/data-sources/{data_source_id}/relay-visibility
{ "relay_visibility": "always" }
```

| Value | Meaning |
| --- | --- |
| `auto` | Follow the rule. The default, and the only value the system ever sets itself. |
| `always` | Keep this source in every read, whatever the rule says. |
| `never` | Hide it outright, even where no direct source covers the span. |

Only the override is stored. Redundancy itself is recomputed per read, because
it depends on what the direct route has actually delivered — and that changes
when a token expires, a backfill lands, or an account is revoked. A stored flag
would go on asserting an answer that had stopped being true.

## Daily aggregates

A second copy does the most damage in a summary. It is not a duplicate row
someone can ignore — it is a wrong number. 7,000 steps read as 14,000, two
nights of sleep for one night, a recovery score counted twice, and nothing
about the figure looks wrong once it is in an analysis.

The daily summaries therefore apply the same rule, to the rows going *into* the
aggregate rather than to its result:

| Endpoint | Deduplicated on |
| --- | --- |
| `/summaries/activity` | samples per series type (steps, energy, distance, HR, floors, active time), including the archived daily rows, plus the workout totals folded in |
| `/summaries/sleep` | sleep sessions per night |
| `/summaries/recovery` | recovery scores per day |

Each takes `include_redundant_relays=true` to count every copy, and each reports
what it left out in `metadata.relay_dedup`. A summary and the records behind it
are resolved with the same spans, so the two never disagree about what counts.

Two deliberate details:

- **The activity summary measures coverage over the archive too**, because it
  reads archived days. Raw sample reads do not: archiving removes the direct
  rows from the live table, and counting archived coverage there would hide the
  relay over days whose direct data the read can no longer return — turning a
  duplicate into a hole.
- **Scores and archived days get a day's tolerance** rather than minutes. A day
  is the unit being deduplicated: a relayed recovery score can land hours from
  the direct one and still be the same day.

Still untouched: `/summaries/body` (latest and averaged readings, not a daily
aggregate), dashboard counts and per-provider statistics, which describe what
was ingested rather than what was measured.

## Limits worth knowing

- **The covered span has a few minutes' tolerance at each edge** (5 minutes for
  samples, 20 for sessions). An aggregator re-timestamps what it relays, so
  without it the copy of the *newest* direct row — the one you are looking at —
  always escapes the rule. The cost is symmetric: when a direct feed stops, the
  relay becomes visible again that much later rather than immediately.
- **Coverage is a span, not a calendar.** Within the requested window the rule
  uses the first and last direct sample per brand and series type. A gap
  *inside* that span — the direct API missing a Tuesday it should have had —
  keeps the relayed copy hidden for the Tuesday too. Re-read with
  `include_redundant_relays=true` when completeness is the question.
- **The unit is a brand, not a device.** With two Garmins both connected
  directly, a relayed Garmin stream that names no device is hidden across the
  span even if it came from the unit that syncs less often. Set
  `relay_visibility: "always"` on that source if it matters.
- **Under `filter_by_priority=true` a redundant relay is not a candidate.** That
  mode returns one source per series type; letting a relay win a type whose rows
  the rule then removes would return an empty series. Sleep is the exception —
  its ranking is per night and applies the rule row by row, so a night only the
  relay recorded still comes from the relay.
- **A read naming no series type gets one coarser span per brand**, since
  measuring coverage for every type would cost a query per type. Every
  timeseries read in practice names its types.
