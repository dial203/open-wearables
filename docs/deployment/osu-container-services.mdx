This guide covers deploying Open Wearables on university infrastructure at The
Ohio State University. It is written for the OSU case but the shape of it —
classify the data, pick a platform that is approved for that classification,
get the application risk-assessed, then deploy — applies at most universities.

<Note>
  Everything below reflects publicly documented OSU service information. Pricing,
  namespace provisioning, and ingress details are behind the authenticated
  service catalog and have to be confirmed with OTDI.
</Note>

## Which OSU service fits

| Service | Fit for Open Wearables |
|---------|------------------------|
| [OTDI Container Services](https://it.osu.edu/otdi-container-services) | **Yes.** Managed Kubernetes with managed PostgreSQL, SSL, DNS, and Shibboleth/DUO integration |
| [OTDI Web Hosting](https://web.osu.edu/) | **No.** Shared LAMP hosting (PHP/MySQL over SFTP) for CMS sites. It cannot run Python services, Postgres, Redis, or long-lived worker processes |
| [Ohio State AWS](https://it.osu.edu/ohio-state-amazon-web-services) / [Azure](https://it.osu.edu/ohio-state-azure) | **Yes, with more work.** University-contracted accounts with integrated billing. You own the whole stack — ECS/EKS or VMs, RDS, ElastiCache, load balancers, patching |

Container Services is the shorter path: a managed cluster, a managed database,
certificates and DNS handled for you, and a platform that is already assessed
against the university's security standards. Ohio State AWS makes sense if you
already have an AWS account for other project work or need services the cluster
does not offer.

## Step 1: Classify the data before anything else

Open Wearables stores per-participant physiological time series plus OAuth
tokens for each participant's wearable account. If those records are
identifiable and collected under a research protocol, they are Research Health
Information, which Ohio State classifies as **S4 (Restricted)** — the
university's highest tier, requiring MFA, encryption, unique accounts,
minimum-necessary access, and access auditing. The platform is used for S4
workloads — OTDI's own requisition instructions use an S4-compliant database
server as the worked example — but that is about the platform, not about your
application on it (see Step 2).

Run the [Institutional Data Policy
calculator](https://it.osu.edu/data/institutional-data-policy) against your
actual data set and keep the output. It determines what the rest of this
process looks like:

- **S4** — the platform must be approved for S4, and the application itself
  needs a risk assessment. Contact `securemyresearch@osu.edu` early; loop in
  your IRB protocol, since where the data lives is a protocol detail.
- **S3 or below** (de-identified, coded with the key held outside the system)
  — materially lighter. Deploying a coded-only instance and holding the
  linking key elsewhere is worth considering on its own merits.

<Warning>
  If any participant is a patient in the Wexner Medical Center context, or the
  data comes from the medical record, it is PHI under HIPAA rather than RHI,
  and the Wexner Medical Center risk assessment team owns that review. The
  rules differ.
</Warning>

## Step 2: Get the application risk-assessed

Ohio State's guidance is explicit: a platform being approved does not approve
the application running on it. An application that interacts with S4 data and
has not already been assessed must be submitted for a risk assessment. For
Open Wearables the assessment will want:

- What the system stores, and for how long (`docs/developer-portal/settings/data-lifecycle`)
- Authentication and authorization model for the portal
- Third-party data flows — each provider's API (Garmin, Whoop, Oura, Fitbit, …),
  and where OAuth secrets and tokens are stored
- Egress: Sentry if you enable it, Resend for transactional email, S3 if you
  enable Apple Health XML imports
- That the source is open and self-hosted, so no participant data leaves
  university infrastructure except to the provider APIs

Start this in parallel with Step 3 — it is usually the long pole.

## Step 3: Request the service

1. Confirm classification and approach with your college IT / security
   coordinator and `securemyresearch@osu.edu`.
2. Get budget approval in Workday. The
   [requisition instructions](https://it.osu.edu/otdi-container-services/create-workday-requisition-container-services)
   spell out the form: **Request Non-Catalog Items → Service**, supplier
   *OTDI – Office of Technology and Digital Innovation*, spend category
   *IT Computer Services - Internet* (SC10518), base price **$20 per unit per
   month**, with a memo noting the price varies with usage. The Internal Memo
   field needs a plain-English business purpose written for an auditor.

   One unit is the **highest** of 1 GB RAM, 3 vCPU, or 10 GB persistent
   storage — the binding dimension, not the sum. The manifests in `deploy/osu/`
   request 1.69 GB RAM and 0.75 vCPU, so RAM binds: 2 units, about $40/month,
   with database storage free until it passes ~17 GB. Consulting time is billed
   separately at $20 per 15 minutes, banked rather than use-it-or-lose-it.
3. Submit the request. Ask specifically for:
   - Development and production namespaces
   - A **managed PostgreSQL** instance (managed Postgres and MariaDB are
     included in the service; Open Wearables needs Postgres)
   - Two DNS names — one for the portal, one for the API. `webtest.osu.edu`
     and `containers.it.osu.edu` are commonly used and managed by the
     Container Services team
   - Whether metering is on resource requests or actual usage, so you can size
     the requisition
   - How to handle secrets (see Step 5)

## Step 4: Understand the deployment model before writing YAML

Container Services is **GitOps via Flux**. You do not `kubectl apply`. Your
namespace comes with a GitLab repository at
`https://repo.service.osu.edu/ContainerService/customer_flux/flux_<namespace>_cs`,
reachable only from OSU IP space. You commit manifests into `production/`, add
each filename to `production/kustomization.yaml`, and the cluster reconciles.

Three platform conventions shape the manifests:

- **Istio, not Ingress.** Routing is a `VirtualService` + `DestinationRule`
  bound to `istio-system/istio-gateway` (public) or
  `istio-system/istio-internal-gateway` (OSU address space only).
- **Apache reverse-proxy sidecar.** Every web-facing pod runs
  `registry.containers.it.osu.edu/ocio/docker-apacheshib-revproxy` on `:8080`
  in front of the application container on `localhost`. It is also where
  Shibboleth SSO is configured, if you use it.
- **No root containers.** Both Open Wearables images ship without a `USER`, so
  each app container needs an explicit `runAsUser`.

Monitoring (pod logs, exec, restart) is at <https://containers.it.osu.edu/>;
team access and usage at <https://containerbilling.org.ohio-state.edu/>.
Neither can deploy — Git is the only path in.

Ready-made manifests following all of this are in
[`deploy/osu/`](https://github.com/the-momentum/open-wearables/tree/main/deploy/osu):
API, portal, Celery worker, Celery beat, and a Redis broker, with every
platform-specific value marked `PLACEHOLDER_`. Mirror the published images into
the OSU registry rather than pulling from Docker Hub.

## Step 5: Settle two things the platform does not solve for you

**Secrets.** GitOps means a Kubernetes `Secret` committed to the Flux repo is
base64 in Git history — encoding, not encryption, readable by anyone with repo
access, permanently. For an S4 deployment holding provider OAuth client
secrets and database credentials, ask Container Services whether they support
Sealed Secrets, SOPS, External Secrets Operator, or an out-of-band Secret
created directly in the namespace, before committing anything real.

**Authentication.** The API hostname serves browser and SDK calls, provider
OAuth callbacks (`/api/v1/oauth/*`), and inbound provider webhooks
(`/api/v1/*/webhooks`). None of those can sit behind Shibboleth: an XHR
redirected to the identity provider fails, and provider webhook calls carry no
OSU identity. So the API host is either public — protected only by Open
Wearables' own bearer tokens — or restricted to the internal gateway, in which
case participants can enroll and sync only from campus or VPN.

<Warning>
  Open Wearables has no MFA of its own, and the Apache Shibboleth sidecar
  cannot protect the API host. If your S4 control set requires MFA, that gap is
  an architecture question for `securemyresearch@osu.edu`, not something the
  platform closes for you.
</Warning>

Shibboleth on the portal host has its own catch: `accept-invite` and
`widget.connect` are participant-facing routes, so SSO there locks out anyone
without an OSU ID. It fits a study staffed and enrolled entirely within Ohio
State, and not much else.

## Step 6: Register OAuth redirect URIs

Provider OAuth applications point at `API_BASE_URL`, so they can only be
registered once the API hostname is live. Each provider's developer console
needs the redirect URI for your deployment — see the
[provider integration guides](/providers/supported). If you put the API on the
internal gateway, provider webhook delivery will not reach it; fall back to
scheduled polling via `SYNC_INTERVAL_SECONDS`.
